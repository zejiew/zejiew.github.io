写作台：给 Hexo 博客一个能自动上传图床的本地 Markdown 编辑器

zejiew2026-11-042026-11-04

写在前面：写博客最烦的其实是配图

写正文本来是最享受的部分。可实际写起来，流程是这样的：

截图存到桌面 → 打开图床网页 → 选文件 → 等上传 → 复制链接 → 切回编辑器 → 粘贴 → 调整一下 Markdown 语法。一篇文章配十张图，这套动作就要重复十遍。中间只要手滑复制错了，还要回去翻图床后台找那张图。

比配图更磨人的是 front-matter。我用的是 AnZhiYu 主题，一篇文章的头部字段有二十多个：top_img 要图片地址还是 false？toc_number 和 toc_style_simple 到底控制什么？swiper_index 填不填？每次 hexo new 之后都要对着主题文档一个个查，查完还得记住「留空等于用主题默认值」这条规矩。

再加上每次想看看效果，要么开一个 hexo s 等它热更新，要么直接推上去看线上——都不算顺畅。

于是就有了这个项目：写作台（hexoblog-md-write-HEXO），一个跑在本机、只干一件事的 Markdown 写稿页——粘贴或拖入图片，自动上传到你的图床，链接直接落回光标处；写完点一下就能构建发布。

项目地址：https://github.com/zejiew/hexoblog-md-write-HEXO---

它长什么样

一句话概括：一个本地网页，长在 source/_posts 上。

几个从一开始就定死的原则：

  • 零依赖：只要有 Node.js 18+，不用 npm install，不连任何 CDN，断网也能写（Markdown 渲染器 marked 已经内置在仓库里）
  • **只绑 127.0.0.1**：它不打算给谁远程访问，就是一个本机的小工具
  • 图片不落地：截图直接进图床，博客仓库里不会多出一堆 images/ 文件夹
  • 图床是你自己的：地址和认证码填在你自己机器上，代码里这两个值是空的，谁 clone 都不会带着别人的图床

走一遍完整流程

第一步，启动。 双击 启动写作台.bat，或者：

控制台会把它找到的东西都打印出来，这一点我觉得比「请手动配置」友好很多：

它会从工具所在目录往上找，找那个同时有 _config.yml 和 source/_posts 的目录当博客根目录。工具放在博客外面也行，--blog 指一下就好。端口被别的程序占了会自动顺延到 8788、8789，以控制台打印的为准。

第二步，挑一篇文章。 左侧列表按修改时间排序，标题取的是 front-matter 里的 title，可以直接搜索。新建、打开、保存都在这一屏完成。

第三步，写。 编辑 / 分栏 / 纯预览三种视图，分栏时滚动同步。工具栏该有的都有：H1–H3、粗体斜体删除线、引用、有序无序列表、行内代码、代码块、链接、表格、分割线，还有一个 <!-- more --> 按钮。

预览用的是 marked，参数按 hexo-renderer-marked 的默认值设置（gfm、breaks、headerIds、mangle）——不是随便渲染一下，是尽量贴近站点上的实际效果。

第四步，贴图。 三种方式：Ctrl+V 粘贴剪贴板里的截图、直接把图片文件拖进编辑区、点工具栏的「插入图片」。上传完成后，链接会直接插到光标位置。

插入格式可以在设置里切换：

格式 效果
Markdown ![图片名](https://…/file/x.png)
HTML <img src="https://…/file/x.png">
纯链接 https://…/file/x.png

还可以勾上「上传后自动复制链接」，这样排版时想手动放到别处也方便。

第五步，填属性。 这一块是我花时间最多的地方，下面单独说。

第六步，保存。 Ctrl+S，直接写回 source/_posts/文件名.md。页面每 3 秒会把未保存的内容存一份到 localStorage，误关标签页后下次打开还能恢复。顶栏那个月亮图标可以切换明暗主题，晚上写东西不刺眼。

第七步，发布。 点发布，它会先保存当前文章，再执行 hexo clean && hexo generate -d，构建日志在右下角抽屉里实时滚动。

26 个 front-matter 字段，终于不用背了

meta 栏下面有一个「文章属性」面板，把 AnZhiYu 主题文档里 Post Front-matter 的字段全部做成了表单：

  • title / date：改了日期会保留原来的时分秒，不会把 Hexo 的排序打乱
  • tags / categories：逗号分隔填写，写回文件时变成 ["a", "b"]
  • description：摘要，首页卡片和 meta description 都用它，面板里有一个「从正文生成」
  • cover / top_img：封面图和顶部大图，都能直接上传，还能用「→顶部 / →封面」一键把地址复制给另一个；也可以填 false 强制关掉
  • comments / toc / toc_number / toc_style_simple / copyright / aside / mathjax / katex / highlight_shrink / aplayer：这些是页面开关，做成了三态——默认（不写字段，跟主题配置走）、开、关
  • swiper_index / top_group_index：首页轮播和推荐卡片的排序
  • 还有 keywords、updated、background、版权模块那一组字段……

几个细节值得说：

留空的字段不会被写进文件，等于用主题默认值。所以不想管的字段，不填就行。

保存时，字段顺序保持你原文件的样子，新增的字段按面板顺序追加。面板里没有覆盖的字段（比如 permalink、某些插件自己的字段）不会被吃掉，原样留在 front-matter 里。这一点我特意写了往返测试来保证——写博客的工具把用户的手写内容弄丢，是不可接受的。

另外也顺手处理了两个编辑器常见的小毛病：文件开头带 UTF-8 BOM，或者丢了第一行的 ---，写作台都能正确读出来，保存时写成标准格式。

为什么非要起一个本地服务？

这是整个项目里最有意思的一个问题。你可能会想：一个网页而已，为什么不能直接在前端把图片 POST 给图床？

因为浏览器读不到响应。

实测 CloudFlare-ImgBed（Cloudflare Pages 部署）的跨域行为是这样的：

  • OPTIONS 预检：返回 200/405，带 access-control-allow-origin: *
  • POST /upload：响应里没有任何 access-control-* 头

也就是说，图片其实已经传上去了，但浏览器拿不到响应体，读不到那个图片链接。预检通过、POST 被拦，属于最容易被误判成「图床挂了」的那一类问题。

顺带还有三个好处：认证码留在本机不经过浏览器、可以给图片指定 uploadFolder、上传失败时能拿到图床返回的真实状态码而不是一句「网络错误」。

不同版本的图床返回的数组/对象不一致，代码里两种都做了兼容。

顺便说说适配：server.js 里上传逻辑集中在 uploadToImgbed() 一个函数。只要你的图床接口长得差不多——multipart/form-data 里一个 file 字段、返回 JSON 里有图片链接——改这一个函数就能接上，前端一行都不用动。PicGo、兰空图床、S3 兼容存储这类都有人这么接过。

发布日志：绕开管道踩过的坑

最初发布功能的实现是 spawn('cmd', [...], { stdio: 'pipe' })，把 hexo 的输出从管道读出来显示。逻辑上没毛病，但在某些受限环境下会直接抛 spawn EPERM——匿名管道被系统策略拒绝了。

现在的做法是完全绕开管道：

stdio: ['ignore', fd, fd]，让子进程自己持有文件句柄往里写；服务端用字节偏移加 StringDecoder 增量读取。这样做的好处是：日志实时滚动、前端断线重连不会重复输出、中文不会被从中间切坏。

如果哪天你看到发布日志只有一行「启动失败：spawn EPERM」，那说明跑的是旧版本，重启一下服务就好。

配置一次，之后就忘了它

第一次打开，点右上角 ⚙️ 设置，填两样东西：图床地址和上传认证码（图床没开认证码就留空）。点保存，会同时写两个地方：

存到哪 作用
浏览器 localStorage 当前页面立刻生效
本机 config.local.json 下次启动自动读取——换端口、换浏览器、清掉站点数据都不影响

「配置一次」是字面意思。优先级是 **界面设置 > config.local.json > config.json**。手改配置文件需要重启服务（或者访问 /api/reload），从界面保存则立刻生效。

关于数据安全，说几句实话

这个工具会直接动你的博客仓库，所以有几条是刻意的：

  • **只读写 postsDir 下的 .md**，文件名做了路径穿越校验
  • front-matter 里不认识的字段原样保留，updated、permalink、插件字段都不会被吃掉
  • 日期没改动就沿用原文件的写法（含时分秒），避免 Hexo 的排序被打乱
  • 保存完 git diff 一眼就能确认改了什么

关于认证码：它明文存在本机 config.local.json 里，这个文件已被 gitignore。服务只监听 127.0.0.1，没有登录鉴权，所以别把 host 改成 0.0.0.0，也别把这个端口暴露到公网。非要在内网用，请自己在前面加一层反向代理和密码。

已知的一处轻微规范化：原文件里空值的 key（比如光秃秃一行 tags:）保存时会被省略。对 Hexo 的行为没有影响。

还有两个自测

写这种「会改用户文件」的工具，光靠肉眼点几下是不够的，所以带了一个最小的测试集：

fm-roundtrip.js 会把 source/_posts 里每一篇读出来、重建一遍、再比对正文和字段——front-matter 有没有丢、顺序有没有乱，它来兜底。也可以指定目录跑：

dom-smoke.js 需要一个已经启动的服务（默认 http://127.0.0.1:8787，可以用环境变量 MDW_BASE 改）。因为是在最小的 DOM 环境里把 init() 跑一遍，它能抓到「选择器拼错了」「初始化抛异常」这类问题——这类 bug 在浏览器里表现就是白屏，很难查。

怎么用起来

  1. 把仓库里的 md-writer/ 目录放到博客里，比如 博客根目录/tools/md-writer/
  2. 双击 启动写作台.bat（macOS / Linux 用 sh start.sh）
  3. 浏览器打开 http://127.0.0.1:8787/，第一次进去填图床地址和认证码
  4. 开写

前提只有一个：**Node.js 18+**。没有 npm install，没有构建步骤，没有后台常驻进程，关掉那个黑窗口服务就停了。

实际效果

下面几张是实际使用时的界面：

最后

这个工具没有任何「平台」的野心。它解决的问题非常具体：我写 Hexo 博客、我用自己的图床、我不想每次配图都切窗口。 所以它只有两个文件值得一看——server.js 负责所有跟本机文件、图床、hexo 打交道的部分，public/app.js 负责界面，中间靠一层薄薄的 /api/ 连着。

代码是 MIT 协议，欢迎拿走改成适合自己博客的样子。如果你的博客不是 Hexo，改 postsDir 指向你的 Markdown 目录也能用；如果用的是别的主题，改 public/app.js 顶部的 FIELDS 表就能加上自己的 front-matter 字段——一条记录就是一个字段名加一个类型。

有 bug 或者想要的功能，直接开 issue 就好。

感谢 CloudFlare-ImgBed 提供的图床接口、marked 提供的渲染能力，以及 Hexo——没有它们，这个工具连一行都写不出来。

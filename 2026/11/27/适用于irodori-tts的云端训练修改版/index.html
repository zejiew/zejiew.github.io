适用于irodori tts的云端训练修改版

zejiew2026-11-272026-11-27

基于irodori TTS Desktop 版本修改，增加后端推理能力，利用腾讯的cloudstudio进行后端推理部署，调用算力来帮助前端训练。

项目地址:https://github.com/zejiew/irodori-cloudtranin-v1

在云端 GPU 上训练与生成

English version: cloud.md

桌面版默认在本机训练 LoRA 适配器、合成语音。云端后端把这份计算搬到另一台有 GPU 的
电脑上：录音、界面、历史记录都留在桌面端，只有计算离开。

它适用于两种情况：

  • 本机没有可用的 NVIDIA 显卡（或显存不足以训练你想要的基座规模），但仍然希望
    在本机决定、在本机验收；
  • 某次训练对桌面端的显卡来说太重，可以租一台机器跑完，得到的音色仍然以本地检查点的
    形式拿回来。

这里的「云端」指什么

没有厂商，也没有账号。后端就是本仓库里的一个程序，由你自己运行在任何有 GPU 的机器
上——实验室服务器、租用的实例、同一局域网内的游戏机：

它运行的是与桌面端完全相同的那份锁定上游代码（train.py、推理运行时、编解码器），
所以那边训出来的检查点在这里能加载，这里做出的音色在那边能说话。协议很小，写在
irodori_tts/cloud/protocol.py 里；其中没有任何东西依赖特定主机，因此可以在前面套上另
一种传输方式（共享目录、SSH 隧道、消息队列）而不必改动应用本身。

部署步骤

  1. 在 GPU 机器上取到本程序及其依赖，包含服务端那组可选依赖：

    训练与生成还需要桌面端所需的一切：torch（CUDA）、上游源码、以及基座模型。服务端按
    以下顺序查找基座：

    • --base-map "v4.1-small=/data/Irodori-TTS-v4.1-Small"（本地目录，或一个
      model.safetensors 文件）；
    • --resources <数据目录>/resources（某个桌面数据目录里已安装的基座）；
    • Hugging Face——从目录中的仓库下载，首次使用时落到 ~/.cache/irodori-cloud。

  2. 带令牌启动。只要监听的不是回环地址，就必须提供令牌；没有令牌时服务端拒绝启动，
    因为一个敞开的端口等于一张敞开的显卡：

  3. 在桌面端打开 设置 → 云端后端：打开开关，填入地址（如
    http://192.168.1.10:7863）与令牌，点 测试连接。返回结果会写明设备型号与 PyTorch
    版本——云端任务运行时，状态栏显示的就是这行内容。

两端必须使用同一个协议版本（也就是同一个构建的本程序）；版本不一致会直接报错，而不是
半好半坏地跑起来。

一个任务经历了什么

  • 预处理始终在桌面端完成：录音、编解码器、编码后的潜变量都在本地。上传的只有潜变量
    （几十 MB）。
  • 训练是服务端把真正的 train.py 作为子进程跑起来，并带 --stop-file，因此
    保存并停止 与本地完全一致：训练器在一个安全边界上写出完整检查点，桌面端再下载它。
  • 任务的事件会镜像进任务自己的日志，所以损失曲线、进度条、剩余时间估算都照常工作。
  • 继续训练 与 恢复 继续的是同一个云端任务：训练器的恢复状态（优化器、随机数
    状态、数据加载位置）留在服务端，从不通过网络传输。
  • 云端跑完的一次训练就是项目里的一次普通训练：照样列出步数、有样本、可导出，也能像其他
    任何音色一样用于生成。

生成走同样的路子：上传参考音频（如果音色是训练出来的，再把适配器打成 zip 一并上传），
服务端合成，wav 连同记录回到 generations/<id>/。批量生成只上传一次参考音频，按条返回
各自的 wav。

可靠性

涉及网络时真正要紧的几点：

  • 每次提交任务都带一个请求 id（X-Irodori-Request）。服务端会记住它：应答丢失后
    重试的客户端，拿到的是它已经启动的那个任务，而不是又开一次训练。上传失败时沿用同一个
    id 重试，总共最多尝试 3 次。
  • 任务目录就是状态本身。 job.json 保存状态、计数与产物；events.jsonl 保存带编号
    的日志。重启后的服务端保留原有任务，并把当时正在跑的任务标记为失败、附上一句说明，而
    不是假装它还在跑。
  • 服务器失联不会把窗口挂死。 连续 5 次轮询失败后，任务以「云端服务器已停止响应」结束；
    服务端此前已发布的检查点会保留下来（等它恢复可达后，下一次轮询会报告）。
  • 停止在安全边界上生效，绝不在写盘中途：用的是训练器自己的停止文件，桌面端等待任务
    进入终态，而不是掐断连接。
  • 产物在投入使用前会先校验：会解压到任务目录之外的 zip 一律拒绝；提前结束的下载会
    重试而不是留下半截文件；适配器只有在 complete.json 标记与权重都在时才会被登记。

成本与限制

  • 默认每张 GPU 同时跑一个任务（Service.concurrency），其余任务排队。
  • 任务目录按 --keep 保留最近若干个（默认 40），更早的连同文件一起清理。
  • 令牌是整个服务端共用的一个密钥，没有按用户区分的账号。请把它当密码对待；不在可信网络
    内时，把服务端放到 VPN、SSH 隧道或做 TLS 终止的反向代理后面。客户端不加任何参数即可
    使用 HTTPS。
  • 桌面端的 本地 API（设置 → 本地 API）是另一回事：它面向本机其他程序提供生成接口，
    与云端后端无关。

无需 GPU 的自检

不用 GPU、不用基座模型、也不用 torch，就能把传输协议和桌面侧的工作进程跑一遍：

selftest 会在真实套接字上起一个真实服务端，只把 GPU 那部分换成桩，然后检查上传、
请求 id 的幂等性、事件顺序、产物下载、工作进程的解包与检查点记录、取消，以及各条错误
路径。

文件

路径 作用
irodori_tts/cloud/protocol.py 双方约定的报文格式与失败类型
irodori_tts/cloud/client.py 桌面端传输层：任务、事件、产物
irodori_tts/cloud/worker.py 桌面侧的计算任务（上传、等待、下载）
irodori_tts/cloud/server.py HTTP 服务：任务注册表、队列、FastAPI 路由
irodori_tts/cloud/runners.py 任务真正执行的东西：训练器、推理运行时

irodori_tts/cloud/check_messages.py 界面消息键的完整性检查
irodori_tts/cloud/add_messages.py 把新增消息写入两种语言的词条表
irodori_tts/desktop/cloud_link.py 窗口侧的视角：设置、载荷、任务标记

部署到腾讯云 CloudStudio

本文说明如何把云端后端跑在腾讯云 Cloud Studio 上，让桌面端把训练与生成交给它。

先说一个决定性前提，它决定了下面的方案形态：

CloudStudio 是「带 GPU 的远程开发机」，不是常驻服务器。
算力按「机时」计费，只要你还开着应用的 IDE 标签页就在消耗；关掉全部 IDE 标签页约
10 分钟后，系统释放算力，服务随之停止。 资源包用尽后不会自动停，而是转按量付费继续扣
绑定账号的余额。

因此本方案的设计是：训练/生成期间保持工作空间开着，跑完就停。这正好匹配
irodori-cloud 的用法——它不是 7×24 在线推理服务，而是一次训练或一次合成。

如果你的目标是一台长期在线、随时可调的推理服务，CloudStudio 不是合适的载体，
见文末「替代方案」。

一、选规格

CloudStudio 的 GPU 规格（2026-08 官方计费页）：

规格 配置 显存 抵扣因子（机时/小时） 单价（元/小时）
GPU T4 8 核 / 32G 16 G 1.2 1.2
GPU A10 20 核 / 116G 24 G 3.3 3.3
GPU V100 8 核 / 40G 32 G 3.6 3.6
GPU L40 48 核 / 192G 48 G 8 8
GPU A800 124 核 / 1929G 80 G 14 14

对照本项目各基座的显存需求（base_models 里的实测包络）：

基座 LoRA 训练（固定 + 每条录音） 纯生成峰值 建议规格
v4.1-small 4.0 GiB + 1.0 GiB 3.3 GB T4（16 G 够用，可开 batch 4~8）
v4-large 13.5 GiB + 3.0 GiB 13.1 GB A10（24 G）起步，L40 更稳

推荐起步：**GPU T4 + v4.1-small**，一小时约 1.2 元，跑完一次小样本 LoRA 通常十几分钟。

有一个坑要先知道：T4 不支持 bf16（计算能力 7.5）。训练器会自己回退到 fp32
（train.py 里有这个判断，会打印一行 warning），代价是更慢、显存约为两倍。所以 T4 上请用
batch_size=1。A10/V100/L40/A800 都支持 bf16。

二、创建应用

  1. 登录 https://cloudstudio.net/，创建应用。
  2. 选 从 Git 仓库导入，粘这个项目的仓库地址；或先用模板起一个空环境再把代码放进去。
  3. 创建后选 GPU T4 规格（或按上表），进入工作空间。
  4. 工作空间首次启动要装依赖，torch 在 GPU 模板里通常已带；没有就跑一次安装（见下）。
  5. 绑定腾讯云账号——首次绑定会送 20 机时，够试很多次。

三、装依赖

在 CloudStudio 的终端里，于项目根目录执行：

[cloud] 只额外装服务端那三个包（fastapi / python-multipart / uvicorn）。torch、上游代码、
模型推理依赖都来自项目本身。

先体检一遍，缺什么会明确列出来：

它会打印 Python 版本、每个依赖是否存在、显卡型号、显存、计算能力、bf16 是否可用，并在
bf16 不可用时提前提示「会用 fp32、请用 batch 1」。

四、启动后端

脚本做的事：

  • 把 HF 缓存与模型放到工作空间目录下（$WORKSPACE/.cache/...），而不是家目录——工作空间
    重置不会连带清掉几个 G 的模型；
  • 令牌只生成一次，存在 $WORKSPACE/.irodori-cloud-token（权限 600）。不要每次启动都换
    令牌    ，否则桌面端保存的那份就失效了；
  • 缺 [cloud] 那三个包时自动补装；
  • 监听 0.0.0.0:7863，并打印出桌面端该填的地址。

它有 autoOpen：应用启动时会通过 .vscode/preview.yml 自动拉起，你不用记命令。

拿到桌面端要填的地址

CloudStudio 的预览 URL 规则是：

例如 https://5adb8439bf8147658b86f063097fa479--7863.ap-shanghai2.cloudstudio.club。

启动脚本检测到这三个环境变量时会直接把它打印出来。关键点：

  • 端口必须与服务实际监听的一致（7863），否则页面打不开；
  • 服务必须监听 0.0.0.0，监听 127.0.0.1 外部访问不到——脚本已经是 0.0.0.0；
  • 这个地址是 HTTPS，客户端的 HTTPS 是自动的，不用加参数。

在桌面端：设置 → 云端后端 → 打开开关 → 填地址与令牌 → 测试连接。

测试连接会同时校验三件事：能否连通、协议版本是否一致、令牌是否正确（/health 本身
不需要令牌，所以客户端会再请求一个需要鉴权的接口来验证凭据）。

五、跑一次训练

  1. 桌面端准备好录音、完成预处理（这一步始终在本机，用的也是本机 CPU/GPU）。
  2. 训练页保持「云端后端」开启，起点选 Irodori-TTS v4.1 Small，填步数。
  3. 开始训练。桌面端上传潜变量（几十 MB），服务端跑 train.py。
  4. 训练期间不要关掉 CloudStudio 的 IDE 标签页——关掉约 10 分钟后算力释放，任务会被
    中断（服务端会把它标记为失败并写明原因）。
  5. 进度、损失曲线、剩余时间在桌面端照常显示。想提前结束就点 保存并停止，训练器会在
    安全边界保存检查点，桌面端随即下载。
  6. 跑完后点工作空间的 停止使用，避免继续扣机时。

六、为什么这样设计（针对 CloudStudio 的限制）

CloudStudio 的事实 方案里的应对
关标签页约 10 分钟释放算力 任务中断时服务端把任务标为 failed 并写明「服务器重启时该任务仍在运行」，桌面端轮询会读到这句话；已发布的检查点不丢
工作空间可能被重置 模型与令牌放在 $WORKSPACE 下；令牌固定，桌面端配置不用改
预览 URL 按端口拼接 端口固定 7863，写进 preview.yml 的 mainPort
只有一台机器、一张卡 服务端默认一次跑一个任务（Service.concurrency=1），其余排队
计费按机时 有 --keep 自动清理旧任务目录；任务跑完提示停止使用
bf16 在 T4 上不可用 训练器自动回退 fp32；体检脚本提前说明
端口对外可访问 强制 --token；--host 0.0.0.0 无令牌时服务端拒绝启动

七、常见问题

页面打不开 / 连接被拒
服务没监听 0.0.0.0，或预览 URL 里的端口和实际端口不一致。preview.yml 的 port: 不
能删（可以留空让系统分配，但那时 URL 里的端口会变）。

测试连接报「令牌被拒绝」
桌面端填的令牌与 $WORKSPACE/.irodori-cloud-token 里的不一致。脚本每次启动会把令牌打印在
终端，直接抄那行。

报 no such device / CUDA 不可用
模板自带的是 CPU 版 torch。装与驱动匹配的 CUDA 版：
https://pytorch.org/get-started/locally/，或换一个 GPU 模板重建工作空间。

显存不足（OOM）
降 batch_size 到 1、确保勾选 gradient checkpointing；v4-large 在 T4 上跑不动，
换 A10 以上。

训练到一半失败，提示服务器重启
IDE 标签页被关掉或断线超过释放窗口。重新打开工作空间、重跑启动脚本，然后在桌面端用
继续训练——云端任务的恢复状态在服务端目录里，前提是工作空间的磁盘没被重置。

费用比预期高
检查是否忘了点「停止使用」。另注意账单有约 2 小时延迟，已经停了也可能还收到提醒。

八、安全提醒

  • 预览 URL 在公网上可达，令牌就是唯一的门。不要把它贴进聊天记录或提交进仓库
    （.gitignore 应当包含 .irodori-cloud-token）。
  • 需要更强隔离时，把 CloudStudio 换成同账号下的 CVM/GPU 云服务器，用安全组只放行你自己的
    IP，或用 SSH 隧道把端口转到本地。
  • 令牌是整台服务器的唯一凭据，没有按用户区分的账号。

九、替代方案（需要常驻服务时）

CloudStudio 适合「我来干活时开一下」。如果你要的是：

  • 7×24 在线的推理 API，桌面端随时调用；
  • 关掉浏览器也不中断的长训练（几十小时）；
  • 多张卡并行、可挂载大容量数据盘；

那么应该用 GPU 云服务器（CVM） 或容器服务，跑同一个
python -m irodori_tts.cloud.server，用安全组/负载均衡暴露端口。此时还需要：

  • 用 systemd 或 supervisor 守护进程，让服务随机器启动并自动重启；
  • TLS 终止（Nginx / Caddy）而不是明文 HTTP；
  • 把 --root 指向独立的数据盘，而不是系统盘。

应用侧不需要任何改动——协议是一样的。

scripts/cloudstudio_check.sh 环境体检：依赖、GPU、显存、bf16
